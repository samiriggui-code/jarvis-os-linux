### ✅ `record_event` sur le chemin critique — corrigé

`usage.py:record_event` était **synchrone** et appelé depuis `async def
_openrouter_complete` (`providers.py:210`) et `_ollama_complete` (`:262`). Base
injoignable → il attendait le timeout psycopg **dans la boucle d'événements** : il ne
retardait pas seulement sa requête, il gelait tout le Core, voix comprise, ~90 s.

Et il n'échouait pas — il attrapait tout et journalisait `usage record failed`. C'est ce
qui le rendait discret : sans tunnel, on croyait à un LLM lent.

**La correction, telle que Samir l'a posée** : la réponse part d'abord, l'écriture se
fait après, ailleurs.

```
LLM → réponse envoyée → (file → fil de fond) → écriture en base
```

Trois décisions dans `usage.py` :

* **file bornée** (512) : base lente → on empile puis on **jette**. Perdre des
  statistiques est acceptable, figer la voix ne l'est pas ; une file non bornée serait
  la même panne en plus lent ;
* **un seul fil d'écriture** : une base à 30 s ne doit pas faire naître trente fils et
  épuiser le pool de connexions avec de la télémétrie ;
* **horodatage à l'enregistrement, pas à l'écriture** : sinon les coûts se décalent vers
  les moments où la base était lente — exactement ceux qu'on veut analyser.

Mesuré : **0,7 ms** pour l'appel (au lieu de ~90 s), la boucle asyncio bat 18 fois par
seconde pendant une écriture de 3 s, 200 appels sur une file de 4 passent en 8 ms avec
195 pertes comptées et signalées. `record_event_sync` reste pour les tests et outils —
**jamais depuis une coroutine**.

⚠ Deux fuites pendant la mise au point : un fil d'écriture déjà lancé continue de vider
sa file dans `session_scope` **tel qu'il est au moment de l'écriture**. Un test qui
simule une base lente puis restaure la vraie envoie donc son rebut en production. 79
lignes `provider='test'` ont été écrites dans `usage_events`, puis **supprimées** ;
la table est revenue à ses 27 lignes. Un test de ce module doit faire la vraie base
**d'abord**, la simulée ensuite, et ne jamais revenir.

`graphify` est **la réponse à « pourquoi graphify ne fait rien »** : il n'y a pas de bug,
il n'a jamais été branché. Voir §5.

### ✅ Approbation sans exécutant — corrigé le 2026-08-05 (P2)

> Ce qui suit décrit l'état **avant** correction. Conservé parce que le
> raisonnement vaut plus que le correctif : c'est le seul défaut de la liste
> qu'on ne pouvait pas voir à l'écran.
>
> Corrigé par `IntentExecutor` + `gravity_for` dans `core/jarvis_core/surface.py`.
> Preuve : `core/.venv/Scripts/python.exe -m jarvis_core._smoke_p2`.
> Détail dans [`architecture/JARVIS-Agentic-UI.md`](architecture/JARVIS-Agentic-UI.md) §9.

L'invariant du produit est **IA → Proposition → Policy Engine → Autorisation →
Exécution**. Les quatre premiers maillons existent. **Le cinquième n'a jamais été
écrit.**

La chaîne est pourtant propre jusqu'à la décision : `__init__.py:1659` reçoit
l'intention, `risk_of` la convertit, `policy.evaluate` tranche, `open_approval`
compose l'`ApprovalCard` **côté Core** (bonne décision — un agent ne peut pas
fabriquer une fausse demande d'autorisation, ni omettre d'en afficher une vraie),
le HUD l'affiche, l'utilisateur répond.

Puis `surface.py:close_approval` retire la demande, retire la carte, rediffuse
l'état. Le `record` contient bien l'`intent` — **mais il n'est relu que pour son
`surface_id`. L'intention est jetée.** Accordée ou refusée, rien ne s'exécute.
Même chose dans la branche autorisée sans confirmation (`__init__.py:1701-1704`) :
un `logger.info("intention AUTORISÉE")`, un accusé, retour.

Conséquence à garder en tête : **le vert « autorisé » ne prouve rien aujourd'hui**.
Tant que le maillon manque, une démonstration d'approbation qui « marche » ne
démontre que l'affichage.

C'est le chantier auquel répond `vendor/eve-analyst-main` : chez Eve,
l'approbation étant une **propriété de l'outil**, la reprise après pause rappelle
l'outil — le lien décision → exécution est structurel, pas à câbler. Voir
[`vendor/README.md`](../vendor/README.md).

C'est aussi l'argument du §7.1 de la vision : construire Mission Control avant d'avoir un
moyen de **prouver qu'une capacité est branchée** industrialiserait ce mode de panne.

### Le montage distribué **est la prod** — ce qui est partiel, c'est le code

Le VPS et le NUC ne sont pas une maquette : c'est l'architecture finale. Ce qui
est encore partiel, c'est l'**avancement du code** — le **Core et le React
(HUD/Dashboard) tournent en local sur le portable** tant qu'il reste à coder et à
corriger. Des **tunnels SSH** relient les trois.

**Pourquoi les services sont déportés :** le portable n'a ni l'espace ni les
ressources pour tout lancer à la fois, alors qu'il faut que *tous* les services
soient up en même temps pour tester les boucles complètes (auth, verrouillage,
voix). Ce n'est donc ni du bricolage ni un état dégradé.

D'où : `jarvis-core.service` et `jarvis-hud.service` sont *inactive/dead* sur le
NUC, et c'est normal. Ne pas les « réparer ».

Constaté le 2026-08-05 :

| Machine | Ce qui y tourne vraiment | Écoute |
|---|---|---|
| **VPS** (`hostinger`) | `voicebox` en docker-compose — `/opt/voicebox-test/voicebox`, *healthy* | `127.0.0.1:17600` |
| **VPS** | `qwen-ollama` en docker | `127.0.0.1:11435` — loopback seul, c'est le point ouvert « exposition d'Ollama » |
| **NUC** (`nuc`) | `jarvis-hermes.service` *active running* | `127.0.0.1:8642` |
| **NUC** | PostgreSQL | `127.0.0.1:5432` (vu en `5433` côté portable, via tunnel) |
| **Portable** | Core, HUD, Dashboard | `8765`, `5173` |

Tout écoute en **loopback** sur ses machines : sans les tunnels, rien n'est joignable.
C'est voulu, et c'est ce qui rend l'exposition d'Ollama un vrai sujet et pas un oubli.

**En fin de session le 2026-08-05, plus aucun tunnel n'était monté** et rien n'écoutait
côté portable — machine redémarrée. Premier geste : remonter les tunnels.

### Monter les tunnels

Joindre le NUC en SSH **ne suffit pas** : PostgreSQL y écoute sur `127.0.0.1:5432`,
loopback seul, et n'est donc exposé à aucune interface. Le SSH fait entrer *sur* la
machine ; le tunnel est ce qui amène le service jusqu'au portable.

```bash
# PostgreSQL du NUC → 127.0.0.1:5433 côté portable (le Core vise ce port)
ssh -f -N -L 5433:127.0.0.1:5432 -p 41222 -i ~/.ssh/jarvis_nuc_ed25519 root@82.66.254.106

# voicebox du VPS → 127.0.0.1:17600
ssh -f -N -L 17600:127.0.0.1:17600 hostinger

# Ollama du VPS → 127.0.0.1:11435  (⚠ n'active RIEN seul : il faut aussi
# décommenter JARVIS_REMOTE_LLM_URL dans core/.env, jamais OLLAMA_HOST)
ssh -f -N -L 11435:127.0.0.1:11435 hostinger
```

Vérifier : `bash -c '</dev/tcp/127.0.0.1/5433' && echo ouvert`.

Sans le tunnel PostgreSQL, **chaque complétion LLM attend le timeout de connexion**
avant de continuer (2,6 s avec tunnel, ~90 s sans). Voir le défaut ci-dessous.

Le 2026-08-05, `known_hosts` portait pourtant une **clé périmée** pour cette adresse :
elle datait d'une machine antérieure derrière la même redirection. Vérifié avant
d'accepter — la clé présentée était identique à celle du NUC en LAN
(`ssh-keygen -F 192.168.1.37`), donc bien le NUC. Entrée remplacée ;
`~/.ssh/known_hosts.old` conserve l'ancienne.

Relancer le Core : `cd core && ./.venv/Scripts/python.exe -u -m jarvis_core`
Libérer le port 8765 d'abord si besoin — un ancien processus qui traîne fait échouer le
bind en silence, et on mesure alors l'ancien code sans s'en apercevoir (piège rencontré).

## 8. Pièges rencontrés — ne pas les repayer

* **Port 8765 occupé** → le nouveau Core échoue au bind, on mesure l'ancien code sans le
  voir. Vérifier le port avant de conclure.
* **Le shell Bash garde son répertoire** entre deux appels. Un `cd core` fausse tout ce
  qui suit — vérifications de fichiers comprises. Utiliser des chemins absolus.
* **`generate_voice_cache.py` est en simulation par défaut** — il faut `--apply` pour
  générer réellement. Protège d'une facturation accidentelle.
* **Un pack vocal sans `manifest.json` est invisible** : `VoiceCache` ne lit que le
  manifeste. Se reconstruit sans resynthèse via `core/scripts/rebuild_voice_manifest.py`.
* **`agent-reach doctor` répond en chinois** et prend ~8 s : décoder en UTF-8 explicite,
  et ne pas l'appeler depuis une sonde (budget 5 s).
* **Le pilotage gestuel synthétise de vrais clics.** Désactivé par défaut depuis le 5/08 —
  `?gestures=1` ou `localStorage.jarvis_gestures = "1"` pour le réactiver.
